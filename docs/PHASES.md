# مراحل کامپایلر TinyAdd

این فایل هر هفت مرحله‌ی کامپایلر را با زبان ساده توضیح می‌دهد: هر مرحله چه کاری می‌کند، ورودی و خروجی‌اش چیست، یک مثال کوچک، و کدام فایل آن را پیاده‌سازی می‌کند.
همه‌ی مثال‌ها را می‌توانید خودتان اجرا کنید؛ مثلاً `./build/tinyadd --stage=lex -e "1 + 2 + 3"` فقط خروجی مرحله‌ی ۱ را نشان می‌دهد.

```
متن برنامه
   │
   ▼
[1] Lexer            → لیست توکن‌ها                 src/lexer.c
[2] Parser           → درخت AST                     src/parser.c, src/ast.c
[3] Semantic         → AST بررسی‌شده                 src/semantic.c
[4] IR generation    → کد سه‌آدرسه (TAC)             src/ir.c
[5] Optimizer        → TAC بهینه‌شده                  src/optimizer.c
[6] Code generation  → بایت‌کد پشته‌ای                src/codegen.c
[7] VM execution     → نتیجه‌ی نهایی                  src/vm.c
```

نکته‌ی مهم طراحی: **هیچ مرحله‌ای خودش چیزی چاپ نمی‌کند و `exit()` صدا نمی‌زند.** هر مرحله فقط داده برمی‌گرداند (یا یک خطا). چاپ همه‌ی خروجی‌ها در `src/trace.c` و تصمیم درباره‌ی ادامه یا توقف در `src/main.c` است. به همین دلیل هر مرحله را می‌شود جدا تست کرد.

---

## مرحله‌ی ۱ — تحلیل لغوی (Lexer)

**چه کاری می‌کند؟** متن برنامه را حرف‌به‌حرف می‌خواند و حرف‌ها را به «کلمه»های زبان تبدیل می‌کند. به هر کلمه یک **توکن** می‌گوییم. مثل وقتی که یک جمله را به کلمه‌هایش تقسیم می‌کنیم.

- **ورودی:** متن برنامه (یک رشته).
- **خروجی:** آرایه‌ای از توکن‌ها. هر توکن نوع (`NUMBER`، `PLUS`، `EOF`، `INVALID`)، متن (lexeme)، شماره‌ی خط و شماره‌ی ستون دارد.

قوانین:
- یک یا چند رقم پشت سر هم ← یک توکن `NUMBER` (مثلاً `42` یا `007`).
- `+` ← توکن `PLUS`.
- فاصله، tab، `\r` و خط جدید نادیده گرفته می‌شوند، ولی شمارنده‌ی خط و ستون جلو می‌رود (tab یک ستون حساب می‌شود و فقط `\n` خط جدید است).
- در آخر همیشه یک توکن `EOF` (پایان ورودی) اضافه می‌شود. محل `EOF` درست بعد از آخرین توکن واقعی است تا پیام خطاهایی مثل «found EOF» به جای قابل‌دیدن اشاره کنند.
- هر حرف دیگری (مثلاً `-` یا `a` یا رقم فارسی `۱`) خطاست و lexer همان‌جا متوقف می‌شود.

**مثال:** `1 + 2 + 3`

```
 #  KIND     LEXEME  LINE:COL
 0  NUMBER   1       1:1
 1  PLUS     +       1:3
 2  NUMBER   2       1:5
 3  PLUS     +       1:7
 4  NUMBER   3       1:9
 5  EOF              1:10
```

نکته: lexer عدد `0` و عددهای خیلی بزرگ را رد **نمی‌کند**؛ فقط می‌داند که «این‌ها رقم هستند». داوری درباره‌ی مقدار عدد کار مرحله‌ی ۳ است.

**فایل‌ها:** `include/token.h`، `include/lexer.h`، `src/lexer.c`

---

## مرحله‌ی ۲ — تحلیل نحوی (Parser)

**چه کاری می‌کند؟** بررسی می‌کند که ترتیب توکن‌ها با **گرامر** زبان جور باشد و از آن یک **درخت نحو انتزاعی (AST)** می‌سازد.

گرامر TinyAdd:

```
program := expr EOF
expr    := NUMBER ( '+' NUMBER )*
```

یعنی: یک عدد، و بعد صفر یا چند بار «`+` و یک عدد»، و بعد پایان ورودی.

parser از نوع **recursive descent** و دست‌نویس است: برای هر قانون گرامر یک تابع C داریم (`parse_program`، `parse_expr`، `parse_number`). قسمت `( '+' NUMBER )*` با یک حلقه پیاده شده که هر بار درخت قبلی را داخل یک گره‌ی `Add` جدید می‌گذارد. نتیجه این است که `+` **چپ‌شرکت‌پذیر** (left-associative) می‌شود: `1 + 2 + 3` یعنی `(1 + 2) + 3`.

- **ورودی:** آرایه‌ی توکن‌ها.
- **خروجی:** ریشه‌ی درخت AST. فقط دو نوع گره داریم: `Num` (عدد) و `Add` (جمع دو زیردرخت).

**مثال:** `1 + 2 + 3`

```
Add
├── Add
│   ├── Num(1)
│   └── Num(2)
└── Num(3)
```

**خطاها:** parser می‌گوید چه چیزی انتظار داشت و چه چیزی پیدا کرد:

| ورودی | پیام |
|---|---|
| `1 + + 2` | `expected NUMBER after '+', found '+'` |
| `1 +` | `expected NUMBER after '+', found EOF` |
| `+ 2` | `expected NUMBER, found '+'` |
| (خالی) | `expected NUMBER, found EOF` |
| `12 34` | `expected '+' or EOF, found NUMBER '34'` |

**فایل‌ها:** `include/ast.h`، `src/ast.c`، `include/parser.h`، `src/parser.c`

## مرحله‌ی ۳ — تحلیل معنایی (Semantic analysis)

**چه کاری می‌کند؟** parser فقط «شکل» برنامه را بررسی می‌کند. این مرحله «معنی» آن را بررسی می‌کند. درخت را پیمایش می‌کند و در دو دور این‌ها را چک می‌کند:

1. **دور اول — هر عدد:** باید بزرگ‌تر از ۰ باشد و در `uint32_t` جا شود (حداکثر `4294967295`). مقدار عددی هر عدد در گره‌ی `Num` نوشته می‌شود (به این کار **annotation** یا حاشیه‌نویسی می‌گوییم).
2. **دور دوم — مجموع:** اعداد از چپ به راست با `uint64_t` جمع می‌شوند و مجموع در هیچ لحظه نباید از `4294967295` بیشتر شود.

اولین خطا (چپ‌ترین) گزارش می‌شود.

- **ورودی:** AST.
- **خروجی:** همان AST با مقدارهای حاشیه‌نویسی‌شده + یک خلاصه (تعداد اعداد و مجموع).

**مثال:** `1 + 2 + 3`

```
✔ 3 literals checked: all > 0, all fit in uint32
✔ total sum 6 fits in uint32
```

**خطاها:**

| ورودی | پیام | محل |
|---|---|---|
| `5 + 0` | `only positive integers are allowed, found 0` | خودِ عدد |
| `1 + 4294967296` | `number 4294967296 does not fit in uint32 (max 4294967295)` | خودِ عدد |
| `4294967295 + 1` | `sum overflows uint32: 4294967295 + 1 = 4294967296 (max 4294967295)` | علامت `+` که باعث سرریز شد |

**فایل‌ها:** `include/semantic.h`، `src/semantic.c`

## مرحله‌ی ۴ — تولید کد میانی (Three-Address Code)

**چه کاری می‌کند؟** درخت را به یک لیست از دستورهای خیلی ساده تبدیل می‌کند. در هر دستور حداکثر **یک عملگر** هست و نتیجه در یک متغیر موقت (`t1`، `t2`، ...) ریخته می‌شود. به این شکل «کد سه‌آدرسه» می‌گویند، چون هر دستور حداکثر سه «آدرس» دارد: دو ورودی و یک خروجی.

قانون تولید:
- `Num(n)` ← خودِ عدد n (بدون دستور).
- `Add(چپ, راست)` ← اول چپ، بعد راست، بعد `tN = چپ + راست`.
- در آخر: `return` نتیجه.

- **ورودی:** AST بررسی‌شده.
- **خروجی:** لیست دستورهای TAC.

**مثال:** `1 + 2 + 3`

```
t1 = 1 + 2
t2 = t1 + 3
return t2
```

برای یک عدد تنها (`42`) فقط `return 42` تولید می‌شود.

**فایل‌ها:** `include/ir.h`، `src/ir.c`

---

## مرحله‌ی ۵ — بهینه‌ساز (Constant folding)

**چه کاری می‌کند؟** هر دستوری که **هر دو ورودی‌اش عدد ثابت** باشد را همان موقع کامپایل حساب می‌کند (fold می‌کند) و از این به بعد به جای آن متغیر موقت، خودِ نتیجه را می‌گذارد (constant propagation). در TinyAdd همه‌ی ورودی‌ها ثابت هستند، پس کل برنامه به یک `return <عدد>` تبدیل می‌شود.

- **ورودی:** لیست TAC.
- **خروجی:** لیست TAC بهینه‌شده + گزارش قدم‌های folding.

**مثال:** `1 + 2 + 3`

```
Before:                After:
t1 = 1 + 2             return 6
t2 = t1 + 3
return t2

folded: 1 + 2 → 3
folded: 3 + 3 → 6
```

با فلگ `--no-opt` این مرحله اجرا نمی‌شود و TAC بدون تغییر به مرحله‌ی بعد می‌رود. این برای مقایسه در ارائه مفید است: بدون بهینه‌ساز بایت‌کد ۶ دستور دارد و با بهینه‌ساز فقط ۲ دستور.

**فایل‌ها:** `include/optimizer.h`، `src/optimizer.c`

---

## مرحله‌ی ۶ — تولید کد نهایی (Code generation)

**چه کاری می‌کند؟** TAC را به **بایت‌کد** یک ماشین پشته‌ای تبدیل می‌کند. ماشین ما فقط چهار دستور دارد:

| دستور | کار |
|---|---|
| `PUSH n` | عدد n را روی پشته بگذار |
| `ADD` | دو عدد بالای پشته را بردار و مجموعشان را بگذار |
| `RET` | عدد بالای پشته را به‌عنوان نتیجه بردار و تمام کن |
| `HALT` | توقف ایمنی؛ codegen هرگز تولیدش نمی‌کند |

چون TAC به ترتیب «اول چپ، بعد راست، بعد عمل» تولید شده، هر متغیر موقتی که لازم داریم همیشه بالای پشته است. پس codegen فقط ثابت‌ها را `PUSH` می‌کند و بعد `ADD` می‌گذارد. (codegen یک مدل از پشته نگه می‌دارد تا اگر روزی این قاعده به‌هم خورد، به جای تولید کد غلط، خطای داخلی بدهد.)

- **ورودی:** لیست TAC.
- **خروجی:** برنامه‌ی بایت‌کد (آرایه‌ای از دستورها؛ آدرس هر دستور شماره‌ی آن در آرایه است).

**مثال:** `1 + 2 + 3` بدون بهینه‌ساز (`--no-opt`):

```
0000  PUSH 1
0001  PUSH 2
0002  ADD
0003  PUSH 3
0004  ADD
0005  RET
```

و با بهینه‌ساز:

```
0000  PUSH 6
0001  RET
```

**فایل‌ها:** `include/bytecode.h`، `include/codegen.h`، `src/codegen.c`

---

## مرحله‌ی ۷ — ماشین مجازی (VM)

**چه کاری می‌کند؟** بایت‌کد را اجرا می‌کند. حلقه‌ی کلاسیک «بخوان ← اجرا کن ← برو بعدی». با `--trace` یا `--stage=vm` وضعیت پشته بعد از هر دستور نشان داده می‌شود.

VM این خطاها را هم بررسی می‌کند (با کد درست هیچ‌وقت رخ نمی‌دهند، ولی ماشین نباید crash کند): stack underflow، stack overflow (حداکثر ۲۵۶ خانه)، سرریز `ADD`، رسیدن به `HALT`، و رد شدن از آخر برنامه بدون `RET`. این خطاها با `error[vm]` و کد خروج `2` گزارش می‌شوند.

- **ورودی:** برنامه‌ی بایت‌کد.
- **خروجی:** نتیجه‌ی نهایی (یک عدد `uint32`).

**مثال:** `1 + 2 + 3` بدون بهینه‌ساز:

```
0000 PUSH 1   stack: [1]
0001 PUSH 2   stack: [1, 2]
0002 ADD      stack: [3]
0003 PUSH 3   stack: [3, 3]
0004 ADD      stack: [6]
0005 RET      stack: []

Result: 6
```

**فایل‌ها:** `include/vm.h`، `src/vm.c`

## بخش‌های کمکی

| فایل | کار |
|---|---|
| `src/main.c` | خواندن گزینه‌های خط فرمان، خواندن فایل، اجرای مرحله‌ها به ترتیب، چاپ خطا و تعیین کد خروج |
| `src/trace.c` | چاپ خوانای خروجی هر مرحله، رنگ‌ها، حالت `--ascii`، و چاپ خطاها |
| `src/diag.c` | ساختار یک خطا (مرحله، پیام، خط و ستون) |
| `src/arena.c` | مدیریت حافظه: همه‌چیز از یک arena گرفته می‌شود و در پایان یک‌جا آزاد می‌شود |

### شکل پیام خطا

هر خطا نام مرحله، پیام، خط:ستون، خط سورس و یک `^` زیر محل خطا را نشان می‌دهد:

```
error[parser]: expected NUMBER after '+', found EOF
  --> 1:4
   |
 1 | 1 +
   |    ^
```

### کدهای خروج

| کد | معنی |
|---|---|
| `0` | موفق |
| `1` | خطای کامپایل (lexer، parser، semantic) |
| `2` | خطای استفاده از برنامه، یا خطای داخلی/VM |

### چرا برنامه‌های خیلی طولانی مشکل ندارند؟

درخت یک برنامه‌ی طولانی مثل یک «شانه»ی بلند به سمت چپ است (`Add` داخل `Add` داخل `Add` ...). اگر با بازگشت (recursion) پیمایش شود، برای ده‌ها هزار عدد ممکن است پشته‌ی C پر شود. به همین دلیل مرحله‌ها «ستون چپ» درخت را با یک حلقه طی می‌کنند (تابع `ast_left_spine` در `src/ast.c`) و فقط برای فرزند راست بازگشت می‌کنند. تست‌ها برنامه‌هایی با ۵۰٬۰۰۰ عدد را هم امتحان می‌کنند.
