## ۱. هدف پروژه

این پروژه برای درس **طراحی کامپایلر** دانشگاه است. استاد خواسته کامپایلری ساخته شود که **تمام مراحلش مو‌به‌مو قابل دیدن باشد و هر مرحله قابل توضیح دادن باشد.**

پس هدف اصلی ساخت یک زبان بزرگ نیست. هدف یک **کامپایلر خیلی کوچک است که درونش کاملاً شفاف است.** هر مرحله باید:

- در فایل‌های جدا و مستقل پیاده‌سازی شود،
- خروجی خودش را به شکل خوانا چاپ کند (به این می‌گوییم trace)،
- در مستندها با کلمات ساده توضیح داده شود.

پروژه فقط یک **ابزار خط فرمان (CLI)** است. هیچ بخش وب، WebAssembly یا رابط گرافیکی ندارد.

## ۲. زبان «TinyAdd»

TinyAdd فقط یک کار می‌کند: **جمع کردن یک لیست از اعداد صحیح مثبت.**

### برنامه‌های معتبر

```
2 + 3
1 + 2 + 3 + 4
42
  10 +   20     (فاصله‌ها نادیده گرفته می‌شوند)
```

یک عدد تنها (`42`) هم برنامه‌ی معتبر است و نتیجه‌اش همان `42` است.

### قوانین

- اعداد **صحیح مثبت و در مبنای ۱۰** هستند. اعشار، عدد منفی و مبنای ۱۶ نداریم.
- تنها عملگر `+` است.
- فاصله‌ی خالی (space، tab، newline) نادیده گرفته می‌شود.
- پرانتز، متغیر و عملگر دیگر نداریم.
- عدد `0` از نظر **lexer معتبر است** ولی **فاز semantic آن را رد می‌کند** با پیام روشن («فقط اعداد صحیح مثبت مجاز هستند»). این کار به فاز semantic یک وظیفه‌ی واقعی می‌دهد.
- عدد خیلی بزرگ هم توسط **فاز semantic رد می‌شود** (بخش ۳.۳).

### گرامر (EBNF)

```
program := expr EOF
expr    := NUMBER ( '+' NUMBER )*
NUMBER  := DIGIT+
DIGIT   := '0' | '1' | ... | '9'
```

parser باید **دست‌نویس و از نوع recursive descent** باشد. استفاده از Lex، Yacc، Bison یا هر کتابخانه‌ی بیرونی ممنوع است.

## ۳. مراحل کامپایلر (قلب پروژه)

خط لوله (pipeline) هفت مرحله دارد. هر مرحله خروجی مرحله‌ی قبل را می‌گیرد.

```
متن برنامه
   │
   ▼
[1] Lexer            → لیست توکن‌ها
[2] Parser           → درخت AST
[3] Semantic         → AST بررسی‌شده (+ خطاها)
[4] IR generation    → کد سه‌آدرسه (TAC)
[5] Optimizer        → TAC بهینه‌شده (constant folding)
[6] Code generation  → بایت‌کد (bytecode)
[7] VM execution     → نتیجه‌ی نهایی
```

### ۳.۱ Lexer
- ورودی: رشته‌ی برنامه. خروجی: آرایه‌ای از توکن‌ها.
- انواع توکن: `NUMBER`، `PLUS`، `EOF`، `INVALID`.
- هر توکن این‌ها را نگه می‌دارد: نوع، متن (lexeme)، **شماره‌ی خط** و **شماره‌ی ستون**.
- هر کاراکتر ناشناخته باید خطا بدهد، با خط و ستون.

### ۳.۲ Parser
- recursive descent و مطابق گرامر بالا.
- خروجی: درخت AST. برای `1 + 2 + 3` شکل پیشنهادی (چپ‌شرکت‌پذیر یا left-associative):

```
Add
├── Add
│   ├── Num(1)
│   └── Num(2)
└── Num(3)
```

- خطاها: مثلاً `1 + + 2` یا `1 +` یا `+ 2`. پیام خطا باید بگوید چه چیزی انتظار می‌رفت و چه چیزی پیدا شد، با خط و ستون.

### ۳.۳ تحلیل معنایی (Semantic)
- AST را پیمایش کن و این‌ها را بررسی کن:
  - هر عدد **بزرگ‌تر از ۰** باشد،
  - هر عدد در نوع داده جا شود (**برای مقدار عددها از `uint32_t` استفاده کن**)،
  - **مجموع کل سرریز نکند** (برای بررسی از `uint64_t` استفاده کن).
- اگر لازم بود، گره‌های AST را با مقدار یا نوع حاشیه‌نویسی (annotate) کن.
- با اینکه زبان کوچک است، چاپ کن چه چیزهایی بررسی شد (مثلاً «۳ عدد بررسی شد: همه > 0 و همه در uint32 جا می‌شوند»).

### ۳.۴ تولید کد میانی — Three-Address Code (TAC)
- AST را به TAC تبدیل کن، با متغیرهای موقت `t1, t2, ...`.
- نمونه برای `1 + 2 + 3`:

```
t1 = 1 + 2
t2 = t1 + 3
return t2
```

### ۳.۵ بهینه‌ساز — constant folding
- عملیاتی که هر دو operand آن ثابت است را همان لحظه محاسبه کن.
- **قبل و بعد** را نشان بده. مثال:

```
Before:                After:
t1 = 1 + 2             return 6
t2 = t1 + 3
return t2
```

- یک گزینه برای **خاموش کردن بهینه‌ساز** بگذار (`--no-opt`) تا در ارائه بشود تفاوت را نشان داد.
- اختیاری: هر مرحله‌ی folding را چاپ کن («folded: 1 + 2 → 3»).

### ۳.۶ تولید کد نهایی (Code generation)
- هدف: یک **بایت‌کد ساده‌ی پشته‌ای (stack-based)**.
- دستورها (حداقلی): `PUSH <n>`، `ADD`، `RET`، `HALT`.
- نمونه برای `1 + 2 + 3` بدون بهینه‌سازی:

```
0000  PUSH 1
0001  PUSH 2
0002  ADD
0003  PUSH 3
0004  ADD
0005  RET
```

- یک disassembly خوانا چاپ کن (آدرس + دستور).

### ۳.۷ ماشین مجازی (VM)
- یک VM پشته‌ای کوچک به زبان C که بایت‌کد را اجرا می‌کند.
- با `--trace`، **وضعیت پشته بعد از هر دستور** چاپ شود:

```
0000 PUSH 1   stack: [1]
0001 PUSH 2   stack: [1, 2]
0002 ADD      stack: [3]
...
Result: 6
```

- VM باید stack underflow و overflow را بررسی کند (با codegen درست هیچ‌وقت رخ نمی‌دهد، ولی باز هم بررسی شود).

## ۵. ساخت و ابزارها

- استاندارد: **C11**. کامپایلر: gcc یا clang. بدون کتابخانه‌ی بیرونی.
- فلگ‌های کامپایل: `-std=c11 -Wall -Wextra -Wpedantic -Werror`.
- هدف‌های `Makefile`:
  - `make` ← ساخت `build/tinyadd`
  - `make test` ← ساخت و اجرای همه‌ی تست‌ها
  - `make debug` ← ساخت با `-g -fsanitize=address,undefined`
  - `make clean`
- باید روی Linux و macOS ساخته شود. پشتیبانی Windows با MinGW خوب است ولی اختیاری. اگر چیزی portable نبود به من بگو.

## ۶. رابط خط فرمان (CLI)

نام فایل اجرایی: `tinyadd`

```
tinyadd <file.tadd>            # کامپایل و اجرای یک فایل
tinyadd -e "1 + 2 + 3"         # کامپایل و اجرای کد از خط فرمان
tinyadd --trace <file>         # نمایش همه‌ی مراحل، قدم‌به‌قدم
tinyadd --stage=<name> <file>  # نمایش فقط یک مرحله: lex | parse | sem | ir | opt | code | vm
tinyadd --no-opt <file>        # بدون بهینه‌ساز
tinyadd --help
```

کدهای خروج: `0` موفق، `1` خطای کامپایل (lexer/parser/semantic)، `2` خطای استفاده یا خطای داخلی.

## ۷. خروجی trace (مهم‌ترین ویژگی)

با `--trace` خروجی باید یک گزارش واضح باشد، یک بخش برای هر مرحله. نمونه برای `-e "1 + 2 + 3"`:

```
═══ Source ═══
1 + 2 + 3

═══ [1] Lexer ═══
 #  KIND     LEXEME  LINE:COL
 0  NUMBER   1       1:1
 1  PLUS     +       1:3
 2  NUMBER   2       1:5
 3  PLUS     +       1:7
 4  NUMBER   3       1:9
 5  EOF               1:10

═══ [2] Parser (AST) ═══
Add
├── Add
│   ├── Num(1)
│   └── Num(2)
└── Num(3)

═══ [3] Semantic analysis ═══
✔ 3 literals checked: all > 0, all fit in uint32
✔ total sum 6 fits in uint32

═══ [4] Intermediate code (TAC) ═══
t1 = 1 + 2
t2 = t1 + 3
return t2

═══ [5] Optimizer (constant folding) ═══
folded: 1 + 2 → 3
folded: 3 + 3 → 6
return 6

═══ [6] Code generation (bytecode) ═══
0000  PUSH 6
0001  RET

═══ [7] VM execution ═══
0000 PUSH 6   stack: [6]
0001 RET      stack: []

Result: 6
```

قوانین:
- هر بخش عنوان و شماره‌ی روشن دارد.
- عنوان‌ها و برچسب‌های خروجی trace **انگلیسی** بمانند (چون ترمینال‌ها با راست‌به‌چپ مشکل دارند)، ولی توضیح مفصل هر مرحله در `docs/PHASES.md` به فارسی است.
- اگر ترمینال Unicode را پشتیبانی نکند، یک فلگ `--ascii` برای نمایش با کاراکترهای ASCII ساده بگذار.
- رنگ: **اجباری** (تصمیم امیرعلی، بخش ۱۵). خروجی‌ها رنگی و زیبا باشند؛ با `--no-color` خاموش شود.

## ۸. پیام‌های خطا

هر خطا باید این‌ها را نشان بدهد: نام مرحله، پیام، خط:ستون، خط سورس، و یک علامت `^` زیر محل خطا.

```
error[parser]: expected NUMBER after '+', found EOF
  --> 1:4
   |
 1 | 1 +
   |    ^
```

```
error[semantic]: only positive integers are allowed, found 0
  --> 1:5
   |
 1 | 5 + 0
   |     ^
```

## ۹. milestoneها (به همین ترتیب، بعد از هرکدام بایست)

1. **اسکلت:** ساخت ساختار کامل پوشه‌ها، `Makefile`، `.gitignore`، ماژول‌های خالی که کامپایل می‌شوند، به‌روز کردن `README`. `make` و `make test` باید کار کنند (حتی بدون تست واقعی).
2. **Lexer** + diagnostics + تست‌های lexer + `--stage=lex`.
3. **Parser و AST** + تست‌های parser + چاپ AST + `--stage=parse`.
4. **تحلیل معنایی** + تست‌ها + `--stage=sem`.
5. **تولید TAC** + تست‌ها + `--stage=ir`.
6. **بهینه‌ساز** (constant folding) + تست‌ها + `--stage=opt` + `--no-opt`.
7. **تولید بایت‌کد و VM** + تست‌ها + `--stage=code` / `--stage=vm`.
8. **گزارش کامل `--trace`**، صیقل دادن پیام‌های خطا، اجرا زیر sanitizerها.
9. **مستندات:** نوشتن `docs/PHASES.md` و `docs/PRESENTATION.md` و `README` نهایی، همگی فارسی.

بعد از هر milestone: بگو کدام فایل‌ها ساخته یا تغییر کردند، چطور اجرا شوند و چطور تست شوند. بعد منتظر بمان.

## ۱۰. تست‌ها

- یک test runner کوچک به زبان C بنویس (بدون فریم‌ورک بیرونی).
- هر مرحله را جدا تست کن و همچنین end-to-end (سورس ← نتیجه).
- حتماً این موارد تست شوند: یک عدد تنها، لیست طولانی، فاصله‌های اضافه، چند خطی، هر نوع خطا (lexer، parser، semantic)، عدد `0`، سرریز (`4294967295 + 1`)، ورودی خالی.
- برنامه‌های تست در `tests/cases/` به‌صورت فایل `.tadd` به‌همراه خروجی مورد انتظار قرار می‌گیرند.

- حالت تعاملی `--step` که بین مراحل منتظر Enter بماند.

## ۱۴. تعریف «تمام شدن» (Definition of Done)

- همه‌ی milestoneها کامل و تست شده‌اند.
- `make test` موفق است. هیچ warning وجود ندارد. زیر AddressSanitizer و UBSan تمیز است.
- `--trace` برای هر برنامه‌ی معتبر هر ۷ مرحله را واضح نشان می‌دهد و برای برنامه‌های نامعتبر خطای خوب می‌دهد.
- مستندات کامل است و با کد می‌خواند.

## ۱۵. تصمیم‌های تأییدشده (پاسخ‌های امیرعلی)

این بخش جواب سؤال‌هایی است که قبل از شروع پرسیده شد. اگر با بخش‌های بالا فرق داشت، این بخش معتبر است.

1. **محیط توسعه:** روی Windows از **WSL با Ubuntu** استفاده می‌شود (`build-essential` و `valgrind`).
2. **ریپو:** فایل‌های پایه (`README.md`، `.gitignore` نسخه‌ی C، `LICENSE` از نوع MIT) از نو ساخته می‌شوند. `git init` محلی انجام می‌شود و ریپوی GitHub به‌عنوان `origin` اضافه می‌شود (بدون push).
3. **`RET` و `HALT`:** codegen در پایان فقط `RET` می‌گذارد (نتیجه را pop می‌کند و VM را متوقف می‌کند). `HALT` در مجموعه‌ی دستورها هست ولی فقط یک توقف ایمنی است و codegen هرگز آن را تولید نمی‌کند.
4. **صفرهای اول عدد:** `007` در lexer معتبر است و مقدارش ۷ است. `000` یعنی ۰ و فاز semantic آن را رد می‌کند.
5. **ورودی خالی یا فقط فاصله:** خطای parser: `expected NUMBER, found EOF` در محل `1:1`.
6. **چند خطا:** کامپایلر با **اولین خطا** متوقف می‌شود و فقط همان را گزارش می‌کند.
7. **`--stage=<name>`:** مراحل قبلی بی‌صدا اجرا می‌شوند، فقط همان مرحله چاپ می‌شود، و بعد برنامه تمام می‌شود (خط `Result:` فقط در `--stage=vm` چاپ می‌شود).
8. **اجرای معمولی (بدون فلگ):** فقط عدد نتیجه چاپ می‌شود، مثلاً `6`.
9. **تست‌های `tests/cases/`:** هر تست یک فایل `name.tadd` و یک فایل `name.expected` دارد که یا نتیجه (`6`) یا متن دقیق خطا را نگه می‌دارد؛ کد خروج هم بررسی می‌شود. test runner مستقیم توابع pipeline را در C صدا می‌زند (برنامه‌ی جدا اجرا نمی‌کند).
10. **حافظه:** یک arena برای هر کامپایل؛ همه‌چیز از آن گرفته می‌شود و در پایان یک‌جا آزاد می‌شود. فایل‌های `include/arena.h` و `src/arena.c` برای این کار اضافه شدند.
11. **رنگ:** خروجی رنگی اجباری است؛ `--no-color` آن را خاموش می‌کند.
12. **فایل‌های اضافه در تست‌ها:** `tests/test.h` (فقط macroهای تست) و `tests/test_arena.c` (تست‌های arena).
13. **`--trace` و `--stage` با هم:** خطای استفاده (کد خروج `2`).
14. **`.gitattributes`:** همه‌ی فایل‌های متنی با پایان خط LF ذخیره می‌شوند تا `Makefile` و سورس‌ها روی Linux/WSL خراب نشوند.
15. **کاراکتر `\r`:** lexer آن را هم مثل فاصله‌ی خالی نادیده می‌گیرد (برای فایل‌هایی که با پایان خط Windows یعنی CRLF ذخیره شده‌اند). `\r` شماره‌ی خط را زیاد نمی‌کند؛ فقط `\n` خط جدید حساب می‌شود.
16. **ادغام با ریپوی GitHub:** چون ریپوی GitHub از قبل commit دارد، اولین pull با `--allow-unrelated-histories` انجام می‌شود و در تداخل‌های `README.md`، `.gitignore` و `LICENSE` نسخه‌ی محلی نگه داشته می‌شود.
17. **محل توکن EOF:** درست بعد از آخرین توکن واقعی (و برای ورودی خالی `1:1`). پس برای `"1 +\n"` خطا در `1:4` و روی خط `1 +` نشان داده می‌شود، نه روی یک خط خالی.
18. **`--stage=lex` با کاراکتر غلط:** اول توکن‌هایی که تا آن لحظه خوانده شده‌اند چاپ می‌شوند، بعد خطا.
19. **ورودی غیر ASCII:** پیام خطا کل کاراکتر و کدش را نشان می‌دهد، مثلاً `unexpected character '۱' (U+06F1)`. بایت‌های کنترلی به شکل `'\x01'` نشان داده می‌شوند.
20. **روشن بودن رنگ:** رنگ فقط وقتی روشن است که خروجی ترمینال باشد. اگر خروجی به فایل یا pipe برود، یا متغیر محیطی `NO_COLOR` تنظیم شده باشد، یا `--no-color` داده شود، رنگ خاموش است.
21. **جریان خروجی:** خطاها در `stderr`؛ نتیجه و trace در `stdout`.

### تصمیم‌های پیاده‌سازی (گرفته‌شده در حین کار)

امیرعلی گفت بدون توقف تا آخر پیش برویم. این تصمیم‌ها در حین پیاده‌سازی گرفته شدند و کد و تست‌ها با آن‌ها می‌خوانند:

22. **متن پیام‌های خطا:**
    - lexer: `unexpected character '-'`، برای غیر ASCII `unexpected character '۱' (U+06F1)` و برای UTF-8 خراب `unexpected byte '\xFF' (not valid UTF-8)`.
    - parser: `expected NUMBER, found '+'` (اول برنامه)، `expected NUMBER after '+', found '+'` یا `found EOF` (بعد از `+`)، `expected NUMBER, found EOF` (ورودی خالی) و `expected '+' or EOF, found NUMBER '34'`.
    - semantic: `only positive integers are allowed, found 0`، `number 4294967296 does not fit in uint32 (max 4294967295)` و `sum overflows uint32: A + B = C (max 4294967295)`.
    - VM: `stack overflow`، `stack underflow: ADD needs two values`، `stack underflow: RET needs a value`، `ADD overflow: result does not fit in uint32`، `HALT reached before RET, no result` و `ran past the end of the program without RET`؛ همه با پسوند `(at address NNNN)`.
23. **کد خروج خطاهای VM و داخلی:** `2` (چون این‌ها خطای برنامه‌ی کاربر نیستند، بلکه نشانه‌ی باگ در کامپایلرند). خطاهای lexer، parser و semantic کد `1` دارند.
24. **ترتیب بررسی‌های semantic:** اول همه‌ی عددها (مثبت بودن و جا شدن در `uint32`) از چپ به راست، بعد مجموع جاری. خطای سرریز مجموع روی همان `+` نشان داده می‌شود که مجموع را از حد بیرون برده است.
25. **برچسب گره‌های AST:** متن اصلی عدد نشان داده می‌شود، مثلاً `Num(007)`، تا کاربر همان چیزی را ببیند که نوشته است.
26. **`--stage=opt`:** TAC قبل و بعد از بهینه‌سازی و لیست folding‌ها نشان داده می‌شود. در `--trace` بخش `[5]` فقط folding‌ها و TAC نهایی را نشان می‌دهد (چون TAC قبلی در بخش `[4]` آمده است). با `--no-opt` بخش `[5]` متن `(disabled with --no-opt: TAC is used unchanged)` را نشان می‌دهد.
27. **بایت‌کد:** آرایه‌ای از دستورها؛ «آدرس» هر دستور همان اندیس آن در آرایه است (`0000`، `0001`، ...). پشته‌ی VM حداکثر ۲۵۶ خانه دارد؛ codegen همیشه پشته را حداکثر ۲ خانه پر می‌کند.
28. **برنامه‌های خیلی بلند:** پیمایش AST روی «ستون چپ» درخت (left spine) با حلقه انجام می‌شود، نه با بازگشت؛ پس برنامه‌ای با ۵۰٬۰۰۰ عدد هم پشته‌ی C را پر نمی‌کند.
29. **فرمت فایل‌های `.expected`:** خط اول `exit: N` (کد خروج) و بعد خروجی دقیق (عدد نتیجه یا متن ساده‌ی خطا بدون رنگ).
30. **خطا همراه با `--trace`:** بخش‌هایی که تا لحظه‌ی خطا کامل شده‌اند چاپ می‌شوند، بعد یک خط خالی و بعد خطا.
31. **`-h`:** نام کوتاه `--help` است.
32. **Windows بدون WSL:** پروژه با w64devkit (GCC برای MinGW) هم ساخته و تست می‌شود. ولی MinGW از AddressSanitizer پشتیبانی نمی‌کند و Valgrind هم ندارد؛ پس `make debug` و Valgrind فقط روی Linux/macOS/WSL اجرا می‌شوند.
