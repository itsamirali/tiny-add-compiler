# سناریوی ارائه

یک دموی کوتاه (حدود ۱۰ دقیقه) برای نشان دادن همه‌ی مراحل کامپایلر. دستورها را به همین ترتیب اجرا کنید. زیر هر دستور نوشته شده چه چیزی را نشان بدهید و چه بگویید.

> قبل از ارائه: `make clean && make && make test` را اجرا کنید تا مطمئن شوید همه‌چیز سالم است. اگر ترمینال کلاس کاراکترهای Unicode را خوب نشان نمی‌دهد، به همه‌ی دستورها `--ascii` اضافه کنید. اگر رنگ‌ها روی پروژکتور خوانا نیستند، `--no-color` اضافه کنید.

---

## قدم ۱ — معرفی زبان (۱ دقیقه)

```sh
cat examples/ok_simple.tadd
./build/tinyadd examples/ok_simple.tadd
```

**بگویید:** «زبان TinyAdd فقط یک کار می‌کند: جمع اعداد صحیح مثبت. گرامرش یک خط است: `expr := NUMBER ( '+' NUMBER )*`. هدف ساختن یک زبان بزرگ نبود؛ هدف این بود که داخل کامپایلر کاملاً قابل دیدن باشد.» نتیجه `5` است.

---

## قدم ۲ — کل خط لوله با یک دستور (۳ دقیقه)

```sh
./build/tinyadd --trace -e "1 + 2 + 3"
```

از بالا به پایین روی خروجی حرکت کنید و برای هر بخش یک جمله بگویید:

1. **Lexer:** «متن به توکن تبدیل شد. هر توکن خط و ستون خودش را می‌داند؛ برای همین پیام‌های خطا دقیق هستند. آخرش همیشه `EOF` است.»
2. **Parser:** «parser دست‌نویس و recursive descent است. درخت چپ‌شرکت‌پذیر است: اول `1 + 2` جمع می‌شود و بعد `3`.»
3. **Semantic:** «اینجا معنی بررسی می‌شود: هر عدد باید بزرگ‌تر از صفر باشد و در `uint32` جا شود، و مجموع هم نباید سرریز کند.»
4. **TAC:** «درخت به دستورهای ساده با متغیرهای موقت `t1` و `t2` تبدیل شد؛ در هر دستور فقط یک عملگر هست.»
5. **Optimizer:** «constant folding: چون همه‌چیز ثابت است، کامپایلر خودش جمع را حساب کرد. `t1` شد `3` و بعد `3 + 3` شد `6`.»
6. **Codegen:** «فقط دو دستور بایت‌کد ماند: `PUSH 6` و `RET`.»
7. **VM:** «ماشین مجازی پشته‌ای اجرا کرد و بعد از هر دستور وضعیت پشته را می‌بینیم.»

---

## قدم ۳ — اثر بهینه‌ساز (۲ دقیقه)

```sh
./build/tinyadd --stage=opt -e "1 + 2 + 3"
./build/tinyadd --no-opt --stage=code -e "1 + 2 + 3"
./build/tinyadd --no-opt --stage=vm -e "1 + 2 + 3"
```

**بگویید:** «دستور اول «قبل» و «بعد» بهینه‌سازی را کنار هم نشان می‌دهد. با `--no-opt` بهینه‌ساز خاموش است: بایت‌کد ۶ دستور دارد به جای ۲، و در VM می‌بینیم که جمع‌ها واقعاً موقع اجرا انجام می‌شوند: پشته `[1]`، `[1, 2]`، `[3]`، ... . نتیجه در هر دو حالت `6` است؛ بهینه‌ساز معنی برنامه را عوض نمی‌کند.»

---

## قدم ۴ — یک برنامه‌ی چندخطی (۱ دقیقه)

```sh
cat examples/ok_list.tadd
./build/tinyadd --stage=lex examples/ok_list.tadd
./build/tinyadd examples/ok_list.tadd
```

**بگویید:** «فاصله، tab و خط جدید نادیده گرفته می‌شوند، ولی شماره‌ی خط و ستون هر توکن درست است.» نتیجه `55` است.

---

## قدم ۵ — خطاها، یکی برای هر مرحله (۳ دقیقه)

**بگویید (قبل از شروع):** «هر مرحله خطای مخصوص خودش را دارد. همه‌ی خطاها یک شکل دارند: نام مرحله، پیام، خط و ستون، خط سورس و یک `^` زیر محل خطا. کامپایلر با اولین خطا متوقف می‌شود و کد خروج `1` برمی‌گرداند.»

### خطای lexer — کاراکتر ناشناخته

```sh
./build/tinyadd --stage=lex examples/err_lexer.tadd
```

```
error[lexer]: unexpected character '-'
  --> 1:7
   |
 1 | 1 + 2 - 3
   |       ^
```

**بگویید:** «`-` در زبان ما وجود ندارد. با `--stage=lex` می‌بینیم lexer تا کجا خواند: توکن‌ها تا قبل از خطا و آخرش یک توکن `INVALID`.»

### خطای parser — ترتیب غلط توکن‌ها

```sh
./build/tinyadd examples/err_parser.tadd
./build/tinyadd -e "1 +"
```

```
error[parser]: expected NUMBER after '+', found '+'
  --> 1:5
   |
 1 | 1 + + 2
   |     ^
```

**بگویید:** «تک‌تک کلمه‌ها درست هستند، پس lexer مشکلی ندارد. ولی ترتیبشان با گرامر نمی‌خواند: بعد از `+` باید عدد بیاید. parser می‌گوید چه انتظار داشت و چه پیدا کرد.»

### خطای semantic — عدد صفر

```sh
./build/tinyadd examples/err_semantic.tadd
```

```
error[semantic]: only positive integers are allowed, found 0
  --> 1:5
   |
 1 | 5 + 0
   |     ^
```

**بگویید:** «از نظر شکل، `5 + 0` کاملاً درست است و parser آن را قبول می‌کند. ولی از نظر معنی غلط است، چون زبان فقط اعداد مثبت دارد. این فرق تحلیل نحوی و تحلیل معنایی است.»

### خطای semantic — سرریز

```sh
./build/tinyadd -e "4294967295 + 1"
```

```
error[semantic]: sum overflows uint32: 4294967295 + 1 = 4294967296 (max 4294967295)
  --> 1:12
   |
 1 | 4294967295 + 1
   |            ^
```

**بگویید:** «هر دو عدد به‌تنهایی مجاز هستند، ولی مجموعشان در `uint32` جا نمی‌شود. کامپایلر برای بررسی از `uint64` استفاده می‌کند و `^` را زیر همان `+` می‌گذارد که باعث سرریز شد.»

---

## قدم ۶ — جمع‌بندی (۳۰ ثانیه)

```sh
make test
```

**بگویید:** «هر مرحله در یک فایل جداست، خودش چیزی چاپ نمی‌کند و فقط داده برمی‌گرداند. برای همین هر مرحله جدا تست شده است، به‌علاوه‌ی تست‌های end-to-end در `tests/cases/`.»

## سؤال‌های احتمالی

| سؤال | جواب کوتاه |
|---|---|
| چرا parser دست‌نویس است؟ | خواسته‌ی پروژه بود و هر قانون گرامر دقیقاً یک تابع C است، پس ارتباط گرامر و کد واضح است. |
| چرا `0` را lexer رد نمی‌کند؟ | lexer فقط شکل کلمه را می‌شناسد (رقم). اینکه مقدار مجاز است یا نه، سؤال «معنایی» است. |
| چرا `+` چپ‌شرکت‌پذیر است؟ | حلقه‌ی parser هر بار درخت قبلی را سمت چپ یک `Add` جدید می‌گذارد. برای جمع نتیجه فرقی نمی‌کند، ولی این قرارداد معمول است. |
| `HALT` کجا استفاده می‌شود؟ | هیچ‌جا در کد تولیدشده؛ فقط یک توقف ایمنی در VM است. codegen همیشه با `RET` تمام می‌کند. |
| حافظه چطور مدیریت می‌شود؟ | یک arena برای هر کامپایل؛ همه‌ی ساختارها از آن گرفته می‌شوند و در پایان با یک `arena_free` آزاد می‌شوند. |
| برنامه‌ی خیلی طولانی چه؟ | مرحله‌ها ستون چپ درخت را با حلقه طی می‌کنند، پس پشته‌ی C پر نمی‌شود (تا ۵۰٬۰۰۰ عدد تست شده). |
